# 搜索性能修复与实测记录

本轮由三个子代理分别完成服务多卷驻留、查询开销和只读基准，主模型单并发构建、回归及实机验证。优化版索引服务已运行，真实C/D库继续保留。用户关闭窗口后，完整Release程序及随附文件已同步至默认启动目录。实际WinUI鼠标键盘和首屏延迟验收仍暂缓。

## 已修改的实现

- 服务将已成功加载或建立的索引按规范化卷根驻留，C/D切换不再互相驱逐；查询固定对应shared_ptr。一个卷执行后台操作时，其它已加载卷继续查询。
- 继续只运行一个Load/Build/CatchUp操作。scheduler按驻留卷轮转，USN查询和索引快照在服务状态锁外执行；没有增加多套worker或扩展IPC。
- Link在Build/Load/Upsert时生成内存派生folded_name，名称查询不再逐条分配Lower字符串；重命名/删除同步维护，BLK5不保存此字段。
- 沿用原有限limit的候选顺序，在过滤范围与内部排除后达到足够有效结果即停止路径解析。全盘查询复用父目录路径，不再为全部匹配项构造完整路径后才截断。

## 同程序、同查询对比

基准为`tests/Blink.Search.Bench/src/main.cpp`，同一可执行文件摘要、当前目录、C→D顺序、关键词、limit200和iterations3。两次各36个样本，包含6个卷切换探测与每类6个普通查询；下表为普通查询的总服务往返中位数，含样本实际遇到的Busy等待，单位毫秒。

| 查询 | 修改前 ms | 修改后 ms | 失败样本数（前→后） |
| --- | ---: | ---: | ---: |
| 无匹配名称 | 355.8 | 55.3 | 0 → 0 |
| 稀疏名称 | 379.5 | 109.3 | 0 → 0 |
| 宽泛名称 a | 4861.8 | 115.7 | 3 → 0 |
| .txt 扩展名 | 1582.6 | 32.9 | 0 → 0 |
| 目录范围内名称 a | 1884.3 | 136.1 | 0 → 0 |

旧版共3个样本在现有5秒IPC期限超时；新版36个样本全部成功。超时样本仅记录到期限，并不表示旧查询实际会在5秒完成。完整原始数据、Busy次数、最后一次RPC、连接和等待分别位于`baseline.jsonl`、`optimized.jsonl`与`benchmark-summary.json`。

本次测量为服务IPC，不能冒充UI首屏或Everything同机对比。基准Busy间隔30ms，当前生产UI为500ms；服务同卷CatchUp/保存仍会产生Busy，重复切卷样本中仍有等待峰值，需要后续优先优化。基准的旧服务进程已运行，新服务重新启动，因此首轮也不作为受控冷启动对比。查询及日志写入时的系统文件变化仍可能影响小样本耗时。

只读检查未在进程、PATH、常见安装位置或SCM发现Everything/ES，未安装或下载，也未全盘搜寻。没有宣称追平Everything。

服务观测working set约533→700MiB，两个时点驻留卷状态不同；这一差值只作开销观察。folded_name约需76–122MiB/百万Link（名称20–40字符，不含分配器开销），多卷常驻还会保留各卷索引本身，详见状态JSON。
